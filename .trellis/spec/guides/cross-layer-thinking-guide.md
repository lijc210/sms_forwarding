# 跨层思考指南

> **目的**：在实现在前，思考跨层的数据流。

---

## 问题

**大多数 bug 发生在层边界**，而不是层内部。

常见的跨层 bug：

- API 返回格式 A，前端期望格式 B
- 数据库存储 X，服务转换为 Y，但丢失了数据
- 多个层以不同方式实现了相同的逻辑

---

## 实现跨层功能之前

### 第 1 步：映射数据流

画出数据如何流动：

```
源 → 转换 → 存储 → 检索 → 转换 → 展示
```

对每个箭头，问：

- 数据的格式是什么？
- 可能出什么问题？
- 谁负责验证？

### 第 2 步：识别边界

| 边界 | 常见问题 |
|------|----------|
| API ↔ 服务 | 类型不匹配、缺少字段 |
| 服务 ↔ 数据库 | 格式转换、空值处理 |
| 后端 ↔ 前端 | 序列化、日期格式 |
| 组件 ↔ 组件 | 属性形状变化 |

### 第 3 步：定义契约

对每个边界：

- 确切的输入格式是什么？
- 确切的输出格式是什么？
- 可能发生哪些错误？

---

## 常见的跨层错误

### 错误 1：隐式格式假设

**坏**：假设日期格式而不检查

**好**：在边界处显式转换格式

### 错误 2：分散的验证

**坏**：在多个层中验证同一个内容

**好**：在入口点验证一次

### 错误 3：泄露的抽象

**坏**：组件了解数据库模式

**好**：每层只了解相邻层

### 错误 4：每个消费者解析相同的载荷

**坏**：命令读取 JSONL 事件并内联转换字段：

```typescript
const thread = (ev as { thread?: string }).thread;
const labels = (ev as { labels?: string[] }).labels;
```

这看起来是局部的，但意味着每个消费者都拥有一份私有的事件契约版本。下次字段变更时，只会更新一个命令而遗漏另一个。

**好**：在事件边界解码一次，然后导出带类型的投影：

```typescript
if (!isThreadEvent(ev)) return false;
return ev.thread === filter.thread;
```

**规则**：对于追加日志、JSON 流、RPC 载荷或配置文件，创建一个所有者负责：

- 事件/载荷类型定义
- 从 `unknown` 转换的类型保护和规范化
- UI 命令使用的元数据投影
- 从数据源回放状态的 reducer

渲染代码可以格式化字段，但不能重新定义载荷契约。

## 跨层功能清单

实现前：

- [ ] 映射了完整的数据流
- [ ] 识别了所有层边界
- [ ] 定义了每个边界处的格式
- [ ] 确定了验证发生的位置

实现后：

- [ ] 测试了边界情况（null、空、无效）
- [ ] 验证了每个边界的错误处理
- [ ] 检查了数据能通过往返传输
- [ ] 检查了消费者导入共享解码器/投影，而不是在本地转换载荷字段
- [ ] 检查了派生状态指向源事件标识符（`seq`、`id`、`version`），而不是发明第二个游标

## 跨平台模板一致性

在 Trellis 中，命令模板（例如 `record-session.md`）存在于**多个平台**中，内容相同或几乎相同。这是一个跨层边界。

### 修改任何命令模板后的清单

- [ ] 查找所有具有相同命令的平台：`find src/templates/*/commands/trellis/ -name "<command>.*"`
- [ ] 更新所有平台的副本（Markdown `.md` 和 TOML `.toml`）
- [ ] 对于 Gemini TOML：调整行延续符（`\\` vs `\`）和三引号字符串
- [ ] 运行 `/trellis:check-cross-layer` 验证没有遗漏

**真实案例**：在 Claude 中更新了 `record-session.md` 以使用 `--mode record`，但忘记了 iFlow、Kilo、OpenCode 和 Gemini——被跨层检查捕获。

---

## 生成的运行时模板升级一致性

某些生成的文件既是文档，也是运行时输入。在 Trellis 中，`.trellis/workflow.md` 由 `get_context.py`、`workflow_phase.py`、SessionStart 过滤器和每轮钩子解析。模板变更必须同时针对全新初始化和升级路径进行验证。

### 修改运行时解析模板后的清单

- [ ] 识别每个读取该模板的运行时解析器，而不仅仅是安装它的文件写入器
- [ ] 检查相关语法是否存在于明显的管理区域（如标签块）之外
- [ ] 验证全新的 `init` 输出和写入旧版 `.trellis/.version` 的版本化 `update` 场景
- [ ] 使用旧的原始模板夹具添加升级回归测试，然后断言安装的文件达到当前的打包形状
- [ ] 更新拥有运行时契约的后端规范

**真实案例**：Codex 内联模式将工作流平台标记从 `[Codex]` / `[Kilo, Antigravity, Windsurf]` 改为 `[codex-sub-agent]` / `[codex-inline, Kilo, Antigravity, Windsurf]`。全新初始化正确，但 `trellis update` 只合并了 `[workflow-state:*]` 块，保留了这些块之外的过时标记。结果：升级后的项目获得了新的钩子脚本，但使用了旧的工作流路由。

## 版本化文档边界

版本化文档是一个跨层边界：源路径、`docs.json` 版本路由和渲染的版本选择器必须描述同一个发布线。

### 编辑版本化文档前的清单

- [ ] 确定目标发布线：stable、beta 或 RC
- [ ] 验证编辑的 MDX 路径与该线匹配：
  - stable：`docs-site/{start,advanced,...}` 和 `docs-site/zh/{start,advanced,...}`
  - beta：`docs-site/beta/**` 和 `docs-site/zh/beta/**`
  - RC：`docs-site/rc/**` 和 `docs-site/zh/rc/**`
- [ ] 验证 `docs.json` 导航将版本标签指向相同的路径
- [ ] 在提交前搜索另一棵树中的发布线特定术语
- [ ] 将出现在根发布路径下的 beta 内容视为源路径 bug，而非渲染 bug

**真实案例**：一个仅限 beta 的任务工作流变更在根 `start/` 和 `advanced/` 路径下记录了 `prd.md` + `design.md` + `implement.md`、任务创建同意和 Codex 模式横幅。结果文档站点在 Release 选择器下提供了 0.6 beta 行为。修复方案：恢复根发布文档，将 0.6 内容移动到 `beta/` 和 `zh/beta/`，并添加对根发布树的 beta 标记搜索审计。

## 模式检测探测清单

当 CLI 通过探测远程资源自动检测模式时（例如，检查 `index.json` 是否存在以决定 marketplace 还是直接下载）：

### 实现前：

- [ ] 探测在使用该结果的**所有**代码路径中运行（交互式、`-y`、`--flag` 组合）
- [ ] 区分 404 和瞬时错误——不要将两者都视为"未找到"
- [ ] 瞬时错误**中止或重试**，永不静默切换模式
- [ ] 当上下文改变时（例如用户切换源），共享状态（缓存、预取数据）**重置**
- [ ] **快捷路径**（例如 `--template` 跳过选择器）必须具有与探测路径相同的错误处理质量——检查下游函数是否没有调用 catch-all 包装器

### 实现后：

- [ ] 追踪从探测结果到模式决策分支的每条路径——不遗漏
- [ ] 外部格式契约（giget URI、原始 URL）已被测试或至少作为注释记录
- [ ] 元数据读取要么读取完整响应，要么使用流式解析器——永不解析固定大小的前缀作为完整 JSON
- [ ] 当从解析的部分重建复合标识符时，验证**所有**字段都包含在内且位于**正确位置**（例如 `provider:repo/path#ref` 而不是 `provider:repo#ref/path`）
- [ ] 验证快捷方式后调用的**操作函数**在内部不使用旧的 catch-all fetch——当错误区分很重要时，必须使用探测质量变体

**真实案例**：自定义注册表流程在 3 次审查中出现了 8 个 bug：(1) 探测仅在交互模式下运行，(2) 瞬时错误落入了错误的模式，(3) giget URI 的 `#ref` 位置错误，(4) 预取模板在源切换时泄露，(5) `--template` 快捷方式绕过了探测，但 `downloadTemplateById` 内部使用了 catch-all 的 `fetchTemplateIndex`，将超时变成了"模板未找到"。

**真实案例**：Agent 会话更新提示使用 `response.read(4096)` 获取 npm `latest` 元数据，然后将其解析为完整 JSON。`@mindfoldhq/trellis` 包元数据超过 4 KB，因此 JSON 被截断、解析静默失败、第一个会话注入没有显示更新提示。修复：在解析之前读取完整响应，并添加一个 `version` 后跟 8 KB 元数据尾部的回归测试。

## 何时创建流程文档

在以下情况创建详细的流程文档：

- 功能涉及 3 层以上
- 涉及多个团队
- 数据格式复杂
- 该功能之前曾导致过 bug

## 事件日志/投影边界

追加日志是跨层契约。单个事件的路径：

```
CLI 输入 → 事件写入器 → events.jsonl → 读取器 → 过滤器 → reducer → 展示
```

### 添加新事件类型或字段后的清单

- [ ] 将事件类型添加到中央事件分类法
- [ ] 在事件层添加带类型的事件变体或类型保护
- [ ] 为来自用户输入或 JSON 的数组/对象字段添加规范化辅助函数
- [ ] 将 `seq`/`id` 赋值保持仅在事件写入器中
- [ ] 让过滤器和 reducer 使用带类型的事件保护，而非本地类型转换
- [ ] 让展示代码使用 reducer 输出或带类型的事件，而非原始 JSON
- [ ] 至少添加一个回归测试，证明历史回放和实时过滤使用相同的过滤模型

**真实案例**：线程频道添加了 `kind: "thread"`、`description`、`context`、labels 和 `lastSeq`。第一次实现正确定义了线程状态，但几个命令仍然使用本地类型转换重新解析事件载荷字段。修复：让核心事件层拥有 `ThreadChannelEvent` 和 `isThreadEvent`，让 `reduceChannelMetadata` 成为唯一的频道元数据投影，让 `reduceThreads` 成为唯一的线程回放 reducer。
