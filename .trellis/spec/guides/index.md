# 思考指南

> **目的**：拓展你的思考，捕捉可能忽略的问题。

---

## 为什么需要思考指南？

**大多数 bug 和技术债务源于"没想到"**，而非能力不足：

- 没想到层边界会发生什么 → 跨层 bug
- 没想到代码模式会重复 → 到处都是重复代码
- 没想到边界情况 → 运行时错误
- 没想到未来的维护者 → 不可读的代码

这些指南帮助你在编码前**问对问题**。

## 快速参考：思考触发器

### 何时思考跨层问题

- [ ] 功能涉及 3 层以上（API、服务、组件、数据库）
- [ ] 数据格式在层之间发生变化
- [ ] 多个消费者需要相同的数据
- [ ] 你不确定某些逻辑应该放在哪里
- [ ] 你在添加事件类型、JSONL 记录、RPC 载荷或配置字段
- [ ] UI/命令代码开始直接转换原始载荷字段

→ 阅读[跨层思考指南](./cross-layer-thinking-guide.md)

### 何时思考代码复用

- [ ] 你正在编写与已有代码相似的代码
- [ ] 你看到同一个模式重复了 3 次以上
- [ ] 你在多个地方添加新字段
- [ ] **你在修改任何常量或配置**
- [ ] **你在创建新的工具/辅助函数** ← 先搜索！
- [ ] 两个文件使用本地类型转换读取相同的无类型载荷字段
- [ ] 多个分支从同一个 `kind`/`action` 更新相同的派生状态

→ 阅读[代码复用思考指南](./code-reuse-thinking-guide.md)

### 验证 AI 交叉审查结果时

- [ ] 审查者声称"用户输入可能有恶意" → 检查实际数据来源（内部清单？用户配置？外部 API？）
- [ ] 审查者标记"缺少验证" → 数据是否来自可信的内部源？
- [ ] 审查者说"行为改变" → 阅读代码注释——是否是有意设计？
- [ ] 审查者指出测试中的"bug" → 在脑海中删除被测试的功能——测试是否仍然通过？如果是 → 同义反复测试

**常见的 AI 审查误报模式**：
1. **信任边界混淆**：将内部数据（打包的 JSON 清单）当作不可信的外部输入处理
2. **忽略设计注释**：将代码注释中记录的有意行为标记为 bug
3. **变量误读**：未将变量追溯到其实际定义（例如，以路径还是名称为键的 Map）

**验证规则**：在确定优先级之前，必须对照实际代码验证每条 CRITICAL/WARNING 发现。AI 审查的误报率预算约 35%。

## 修改前规则（关键）

> **在更改任何值之前，务必先搜索！**

```bash
# 搜索你要更改的值
grep -r "value_to_change" .
```

这一个习惯可以防止大多数"忘记更新 X"的 bug。
